# Application principal threat model

## Authority model

| State | Sole writer | Readers |
|---|---|---|
| Principal capability, resource assignment, expiry, revocation | tenant-admin principal management routes | application auth middleware, operators |
| Credential hash, expiry, revocation | tenant-admin principal management routes | application auth middleware |
| Agent, encrypted keys, public addresses, application binding | `Vault.ensureApplicationWallet` atomic command | application address command, operators |
| Durable operation idempotency | owning application command transaction | owning command on replay |
| Prepared transaction intent | proposal-only persistence module | proposal command, future separately authorized consumer |
| Proposal | proposal-only persistence module | exact-scope `transaction:proposal:read`, or immutable exact pre-0026 proposal/resource compatibility tuple; future separately authorized consumer |
| Signature/broadcast state | existing Vault/execution authorities; **not this boundary** | existing consumers |

The durable authenticated principal ID is the immutable audit actor. Credential selector, capability, request ID, and resource IDs are derived from server context and command results, never caller identity fields.

## Protected assets

Private keys, signatures, broadcasts, approvals, tenant administration, policy management, arbitrary wallet/agent assignment, secrets, webhooks, and resources assigned to other principals or tenants.

## Attacker model

Assume an attacker fully compromises the product backend and steals its application credential. It can choose arbitrary methods, paths, headers, IDs, bytes, idempotency keys, request timing, and concurrent replicas. It cannot write Steward's database directly.

## Invariants

1. Application credentials authenticate only the five exact capability-gated `/application/*` operations.
2. `application-principal` never satisfies tenant-level or agent-access helpers.
3. The global deny guard runs before every non-application handler and resource lookup.
4. Capabilities and status are closed PostgreSQL enums and exact-match runtime values; no wildcard/prefix/case normalization exists.
5. Every application relation and lookup carries both tenant and principal scope; composite foreign keys reject cross-scope composition.
6. Assigned resources, wallet bindings, idempotency records, intents, and proposals reject updates.
7. Wallet ensure atomically commits agent, encrypted EVM/Solana keys, EVM/Solana addresses, binding, and idempotency—or no rows.
8. Full resource tuples are stored and compared. A deterministic-ID collision never reassigns or returns an occupied wallet.
9. All writes require durable PostgreSQL idempotency scoped by tenant, principal, operation, and key.
10. Proposal persistence has no signing/RPC/approval/broadcast import and writes neither `transactions` nor `approval_queue`.
11. Exact proposal IDs cannot be consumed by any legacy sign/approve/reject route.
12. Proposal reads require an exact read capability and tenant/principal/resource scope; foreign and unknown IDs are enumeration-resistant. A persisted `proposed` row is non-terminal, and execution evidence remains explicitly `unknown` until a canonical linkage exists.
13. Credential/principal revocation and expiry are read from authoritative storage on every request.
14. Unknown/malformed/revoked/expired credentials share a generic response; every attempt performs one selector lookup and one timing-safe comparison, with a dummy hash on misses.
15. Raw secrets are returned only once at create/rotate and never stored, logged, or audited.

## Abuse cases and controls

| Abuse case | Control | Test evidence |
|---|---|---|
| Call any legacy/public/admin route | global namespace deny + distinct auth type | dynamic enumeration of every mounted method/path plus explicit custody matrix |
| Smuggle execution fields | strict schemas reject unknown keys | `broadcast`, approval, signature, signed transaction, status, actor and scope field matrix |
| Create arbitrary wallet/reassign agent | immutable assigned resource + no caller agent input | unassigned resource and ownership-mutation tests |
| Cross principal/tenant composition | composite foreign keys and predicates | direct foreign-key rejection and cross-principal 404 tests |
| Race wallet creation | one Vault transaction + PostgreSQL idempotency | concurrent ensure and injected-failure rollback tests |
| Replay changed transaction | canonical hash + scoped operation idempotency | replay, payload drift, cross-operation, and real PostgreSQL concurrency tests |
| Enumerate keys | high-entropy selector, uniform lookup/compare/failure, auth rate limit | malformed/unknown/wrong/expired response assertions and static middleware review |
| Forge audit identity | actor/credential identity from authenticated context | audit actor and metadata assertions; strict forged-field rejection |
| Enumerate or over-read proposals | exact capability plus tenant/principal/resource-scoped join; uniform foreign/unknown 404 | cross-principal, cross-tenant, unknown, malformed, revoked, and expired matrix |
| Mistake proposal for execution | non-terminal `proposed`; explicit unknown execution evidence; separate tables/module | read contract, replay, zero mutation, zero Vault calls, and zero transaction rows |
| Turn proposal into execution | separate tables/module; proposal IDs absent from executable state | exact-ID sign/approve/reject matrix, zero Vault calls and zero transaction rows |
| Break migration on live data | additive schema and no legacy-row rewrite | migration test over populated two-tenant agents/transactions |

## Residual risks

- SHA-256 is appropriate only because application secrets are uniformly random 256-bit values.
- Database-superuser compromise can bypass constraints/triggers. Database access remains a separate privileged boundary.
- The per-process authentication limiter complements upstream limits; deployment ingress must retain global abuse controls.
- Any future proposal consumer is a new execution authority and requires its own authorization, replay, approval, and threat-model review. Application credentials must never authorize that consumer.
